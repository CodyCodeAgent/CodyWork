# 群内方案协作

在「设置 → 飞书机器人 → 群内方案协作」按群 ID 配置。先让本机器人在目标群绑定一个真实需求/工作空间会话，然后选择这个绑定，目前仅支持 Codex 会话（要求逐轮只读权限），开启协作，设置最大轮次（1–30，默认 3）及分钟时限（1–120，默认 15）。群和发起人仍需通过该机器人的访问策略。

双方都需升级并配置同一群。无需维护机器人名单：真人同时 @ 本次参与的 2–8 个机器人，说明要讨论的方案，平台通过当前应用看到的群机器人身份校验参与者。没有被 @ 的机器人不会加入；普通机器人消息不会作为人类操作指令执行。

飞书应用需增加 `im:message.group_at_msg.include_bot:readonly`，发布版本并完成租户授权。仅有原来的用户 @ 权限无法接收机器人互相 @ 的消息。卡片消息通过原始卡片内容读取接口恢复协作元数据。

## 使用

- 在群里发送「@甲 @乙 请讨论这个方案，找出遗漏和分歧」。每个机器人使用自己的绑定会话上下文。
- 所有参与方加入后开始；一轮指每个参与机器人完成一次判断。双方设置不同，采用较小的轮次上限和较早的截止时间。
- AI 输出实质方案、判断无需补充，或请求人工决定。平台记录待解决问题；不能将有未解决问题的判断当成已完成。
- 加入和结束状态使用简短状态卡片同步。同一轮所有机器人都判断完成后，不再调用模型；某方仍提出问题时，其余参与者下一轮重新判断。方案正文只在模型给出内容时出现。
- 活跃话题中 @ 机器人补充信息会保留在本批次，不重置额度；建议同时 @ 所有参与者，使各方获得相同补充。执行中的当前轮使用开始时上下文，补充供下一轮读取。如果本地当前轮判断已经发出，平台停止旧讨论并提示显式重开，避免用旧的 done 判断错误收敛。
- `/协作重开` 并 @ 全部参与者：停止原批次，以新消息 ID 创建新批次。已经结束后再次 @ 全部参与者，也会新建批次。旧消息不能恢复已结束批次。
- @ 机器人发送 `/stop` 或 `/协作停止`，或在 Work 讨论记录中点击「停止讨论」。平台取消本批次的后续提交，只有当前实际运行的协作 Turn 才会被中断，不打断其他人工 Turn。
- 讨论仅提交 read-only 执行档位；不改变原会话权限或其他来源设置。需要审批/问答时停止自动讨论，转人工处理。

## 实现与恢复

Core 的 `channel/collaboration` 提供版本化事件、结构校验、轮次归并和终态规则。Work 负责群配置、身份授权、绑定、SQLite 讨论元数据及 UI。

机器人没有主持人。每台机器独立运行相同协议，以真人发起消息 ID 为批次标识，以发起消息中的机器人提及顺序分配参与槽位。跨应用 Open ID 不能直接互用；每台机器用自己的群机器人列表和消息发送者身份校验槽位。

加入/判断/停止事件通过已有持久化 Outbox 发送，协议保存在卡片按钮 value 中，不展示机器 JSON。乱序事件先持久化，按当前轮次归并。重复事件按批次、参与槽位、轮次去重。接收还检查实际群和话题；发送前重新校验批次权限与截止时间，过期卡片不会因 Outbox 重试发出。讨论元数据不代替原生 Thread 历史。AI 执行仍经过 Inbox → ConversationCommandGateway → ConversationProjectionHost，审批和停止沿用现有入口。Core 队列在真正启动原生 Turn 前重新调用宿主有效性校验，停止/过期后已排队任务不会迟到执行。

重启恢复使用原有 Inbox / native Turn 对账，不能重新提交 admission 不确定的命令。未交付协作事件可重试；失联参与方不会无限等待，截止后结束。失效绑定、权限撤销、无效模型 JSON、执行失败会停止或进入人工处理。

## 验证与发布

本次 Core 源码与 Work 同时修改。Work 当前仍基于 v0.45.0，通过已有 pnpm patch 包含新 Core 协议构建产物，并保留原 Fast 支持补丁；可直接进行本地安装和验证，不依赖尚未发布的 tag。后续发布 Core tag 后可迁移依赖并移除已上游的补丁片段。

本地测试使用两套独立数据库及应用身份，模拟飞书投递；真实飞书跨应用身份、权限和卡片读取仍需获授权的专用测试群联调。模拟测试不等于真实飞书验收。
