# 定时跟进与通知

## 使用

在需求或 Workspace 会话中明确要求 AI：每隔多少分钟检查哪些任务、满足什么条件结束、最晚何时停止、通过哪个机器人通知谁。AI 使用内置 `codywork_followups` 工具创建，工具成功返回任务 ID 才表示安排成功；它不会在对话中运行 sleep 或系统 cron。

支持每次通知（every）、有变化通知（change）、仅结束通知（terminal）。未指定时默认 change 并在创建回执说明。变化比较结构化业务事实和状态，不比较摘要措辞。查询失败不是“没变化”。截止时间必须带时区且晚于当前时间。

「设置 → 定时跟进」统一管理任务；会话标题旁的「定时跟进」自动带入来源会话。可以修改、暂停、恢复、取消、立即检查、查看来源与后台历史、运行记录及投递状态。取消需二次确认，不撤销已经发出的外部任务。

## 执行与隔离

- 一个任务对应一个原生 Codex fork 会话，在来源一轮结束后创建。fork 继承当时的历史，不自动同步来源之后的新消息；创建过程失败会在下次检查前重试准备。
- 只读检查走原有 ConversationCommandGateway 的 schedule 来源，执行、事件与审批仍由 Core 管理。不保存第二份对话历史。
- fork 隔离会话，不隔离文件或外部系统。原生只读模式保护本地文件；外部 CLI/API 仍依赖其自己的权限。提示明确禁止重提业务、部署、写入或递归创建跟进。平台不声称网络请求天然只读。
- 后台会话不能升权、手动发起其他任务或写入快捷指令。需要人工回答、授权或单次检查超过五分钟时转为待处理。
- 每次提交前校验任务状态、截止时间和运行身份；准备阶段的取消和超时也会阻止迟到提交。

## 持久化与投递

任务和运行元数据持久化在 SQLite；调度器使用事务租约和心跳防重入。错过多轮只执行一次，不补跑风暴。失去租约的未知执行不会自动重发，需人工处理。

检查结果先保存，飞书通知复用持久化 channel Outbox。每次通知使用运行 ID 去重，投递失败仅重试通知，不重新检查业务。通知达到死信状态可点击「重试通知（不重新检查）」。后台检查不会再触发长任务智能通知。

机器人和接收人可继承 Workspace 智能通知的已保存目标，但定时跟进不受其启用状态及长任务时长门槛约束。接收人 Open ID 必须属于选中的机器人应用。关闭浏览器不会停止调度，服务器必须持续运行；配置 `CODYWORK_PUBLIC_ORIGIN` 后通知才携带可访问的原会话链接。

当前只支持具备原生 fork 的 Codex Runtime。未支持 fork 的 Runtime 会明确拒绝创建，不会伪装成独立会话。
