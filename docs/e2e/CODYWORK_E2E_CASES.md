# CodyWork 自然语言 E2E 回归用例

## E2E-001 页面启动、身份验证与 Workspace 恢复（P0）

前置条件：使用一个已经登记的测试 Workspace；浏览器中没有当前站点的临时页面状态。

步骤：

1. 打开 CodyWork 根地址。如果出现登录页，输入测试环境密码并登录。
2. 选择测试 Workspace，进入概览页。
3. 刷新页面，再关闭并重新打开同一地址。
4. 新开一个同站点 Tab，确认两个 Tab 都能进入应用。

关键断言：

- 正确密码可以进入，错误密码有明确错误且不会进入应用。
- 登录状态和所选 Workspace 在正常有效期内持久化，不应无缘无故反复要求密码。
- 刷新后仍恢复到同一 Workspace，不出现空白页或错误 Workspace。
- 页面最终显示实时连接成功；没有无限“连接中”。

## E2E-002 Workspace 与仓库发现

前置条件：准备一个包含多个 `services/` Git 仓库的测试 Workspace，其中至少一个干净、一个有未提交修改。

步骤：

1. 从 UI 新建或登记 Workspace。
2. 等待后台扫描结束，查看概览的仓库数量和仓库列表。
3. 进入仓库管理，搜索一个仓库名，再清空搜索。
4. 刷新页面并再次查看状态。

关键断言：

- 首次扫描有明确进度，结束后数字和列表一致。
- 搜索结果只包含匹配仓库，清空后恢复完整列表。
- clean/dirty 状态与真实 Git 工作区一致。
- 后台刷新不会清空已经显示的数据，也不会重复创建仓库记录。

## E2E-003 创建多仓库 Demand 与 Worktree

前置条件：至少两个干净的测试仓库；使用本轮唯一的 Demand 名称和分支名。

步骤：

1. 点击“新建需求”。
2. 在 Repo 选择器中分别搜索并勾选两个仓库。
3. 创建 Demand，等待 Worktree 初始化完成。
4. 查看 Demand 顶部路径、仓库信息和侧边栏条目。
5. 从 Demand 工具箱打开“添加已有 Repo”，分别按项目名、路径和默认分支搜索；检查无结果、清空和重新打开弹窗的状态。
6. 选择另一个 Repo 并添加，等待 Worktree 初始化完成。
7. 在文件系统只读核对所有 Worktree 的分支和基线。

关键断言：

- Repo 列表支持搜索和多选，已选项不会因搜索条件变化而丢失。
- “添加已有 Repo”只搜索尚未加入的项目，显示匹配数量；隐藏的单选项不会被误提交，清空搜索恢复列表，重新打开时不残留旧查询。
- 每个仓库创建独立 Worktree，路径和分支正确。
- Demand 页面只允许会话写入自己的 Worktree，不把基线仓库当作工作目录。
- 重复点击创建不会产生重复 Demand 或半成品 Worktree。

清理：从 UI 删除测试 Demand/Workspace 绑定，并只删除明确属于本用例的一次性 Worktree。

## E2E-004 Demand 专属 URL 与刷新恢复（P0）

前置条件：存在一个至少有两个会话的 Demand。

步骤：

1. 从需求列表进入目标 Demand，复制浏览器地址。
2. 在新 Tab 直接打开该地址。
3. 刷新页面，并使用浏览器前进/后退在概览和 Demand 之间切换。

关键断言：

- URL 同时携带 Workspace 和 Demand 身份，能够直接分享和访问。
- 直接打开或刷新后仍进入同一 Demand，而不是概览或其他需求。
- 会话列表、当前会话和历史消息能够恢复。
- 前进/后退不会产生重复历史或丢失选中态。

## E2E-005 基线同步与脏状态清理

前置条件：一个测试仓库基线包含可丢弃的未提交改动；对应 Demand Worktree 另有一份应保留的改动。

步骤：

1. 在概览确认基线仓库标记为 dirty。
2. 打开仓库工具，查看“基线有改动”的解释和清理入口。
3. 触发清理，先验证存在明确的破坏性确认，再确认执行。
4. 在概览页对单个干净仓库执行“同步”，观察该行的同步结果。
5. 为多个测试仓库分别准备“落后远端”“已是最新”“dirty/不可同步”状态；再准备一个处于 detached HEAD、但 `origin/HEAD` 可指向 `master` 或 `main` 的仓库。
6. 执行“同步全部”，在后台仓库扫描同时发生时持续观察逐仓库进度和最终汇总。
7. 检查所有基线和 Demand Worktree，刷新页面后再次核对仓库状态。

关键断言：

- 清理按钮只针对基线仓库，并明确说明会丢弃哪些未提交内容。
- 未确认前不发生任何文件变化。
- 确认后基线恢复干净；Demand Worktree 的改动完全保留。
- 同步只在可快进时更新本地基线；冲突或不可快进时给出错误，不强制重置。
- “同步全部”逐仓库执行并汇总更新、已是最新、跳过和失败数量；单仓库失败不应中断其他仓库。
- 后台仓库扫描与批量同步并发时，任何已登记仓库都不会短暂消失或误报“Repo 不存在或已不在当前 Workspace 中”。
- detached HEAD 仓库应从 `origin/HEAD`（缺失时回退 `master`、`main`）识别同步目标，并仍然只允许安全快进。
- 单仓库按钮和批量同步使用相同的安全语义；运行期间不能重复发起同步或清理。

## E2E-006 导航、会话管理与折叠状态

前置条件：当前 Workspace 至少有两个 Demand，每个 Demand 至少两个会话。

步骤：

1. 折叠最左侧工作台导航，再展开。
2. 折叠 Demand 内的会话栏，再展开。
3. 在不同 Demand 和会话间切换。
4. 新建会话、修改会话名，并尝试删除会话。
5. 刷新页面。

关键断言：

- 折叠入口位置稳定、可发现，折叠后为正文释放空间且仍有明确展开入口。
- 切换不会串消息、串 Worktree 或串运行状态。
- 重命名立即更新且刷新后保留。
- 运行中/待审批会话不能被误删；每个 Demand 至少保留一个会话。
- 删除的是 CodyWork 绑定时，文案明确说明原生 Codex Thread 是否保留。

## E2E-007 用户消息立即出现、正式消息收敛（P0）

前置条件：一个空闲会话；使用一个至少等待数秒才回复的无副作用 Prompt。

步骤：

1. 在输入框输入唯一文本并发送。
2. 在模型产生任何回复之前立即观察时间线。
3. 等待 `turn/start` 和正式 user item 到达。
4. 等待回复结束后刷新页面。

关键断言：

- 消息进入本地 outbox 后立刻显示 optimistic 用户气泡，不等待模型 response。
- 正式 user item 到达时原位替换 optimistic 气泡，不新增第二条。
- 回复前、回复中、回复后和刷新后都只有一条该用户消息。
- 启动失败时 optimistic 气泡被移除，failed outbox 保留并提供重试；不能静默自动重发。

## E2E-008 回复完成后的顺序与去重（P0）

前置条件：使用一个会产生 assistant 文本和工具调用的会话。

步骤：

1. 连续完成三轮带唯一标识的问答，其中至少一轮包含工具调用。
2. 每轮结束后记录用户消息、assistant 回复、工具卡片和 Worked 分隔条的顺序。
3. 等待实时 overlay 回流，再刷新页面。
4. 将 Tab 保持打开一段时间后再发送第四轮。

关键断言：

- 每个 Turn 的用户消息、活动项、assistant 回复和终态属于同一轮，不跨轮穿插。
- 同一 `turnId` 的历史消息与实时 overlay 收敛为一份，即使二者 item ID 体系不同。
- 不出现重复 assistant 内容、重复 Worked、重复 Stopped 或旧回复堆到最新消息之后。
- 不跨 Turn 仅按相同文本去重；不同轮次有意相同的回答应各自保留一条。

## E2E-009 输入键盘、排队与 Skill 引用

前置条件：存在两个可调用 Skill；会话空闲。

步骤：

1. 在输入框输入两行文字，按 Enter 换行。
2. 输入 `$`，选择两个 Skill，确认都显示为引用。
3. 按 Control+Enter 发送。
4. 在回复仍运行时发送第二条消息。
5. 等第一轮结束并观察第二轮启动。

关键断言：

- Enter 只换行，Control+Enter 才发送。
- 一条消息可引用多个 Skill；不依赖单选下拉框。
- Skill 以结构化引用进入请求，而不是只拼接名称文本。
- 活跃 Turn 期间的新消息进入队列，页面立即可见且不会覆盖输入草稿。
- 第一轮结束后队列消息只执行一次。

## E2E-010 停止、失败 outbox 与重试

前置条件：一个可以持续运行数秒的无副作用任务。

步骤：

1. 发送任务，等待进入运行中，然后点击停止。
2. 观察 Turn 终态、输入框和时间线。
3. 构造一次明确的启动失败或上游失败，再点击“重试此消息”。

关键断言：

- 主动停止显示一次“本次回复已停止”或等价状态，不显示两条 `Stopped`。
- 会话回到可发送状态，停止不被当作普通失败，也不自动把旧内容塞回输入框。
- 失败消息保留可重试 outbox；点击重试只重新发送一次。
- 页面刷新后终态稳定，不重新变为 running。

## E2E-011 浏览器实时连接与多 Tab（P0）

前置条件：同一用户在同一浏览器打开两个 CodyWork Tab。

步骤：

1. 两个 Tab 打开相同或不同 Demand。
2. 在 Tab A 发一条消息，观察 Tab B 和连接状态。
3. 暂时中断浏览器到 CodyWork 的 WebSocket，再恢复网络。
4. 等待自动重连并刷新历史。

关键断言：

- 两个 Tab 可以同时保持连接，不能互相踢掉或导致 App Server 重启。
- 连接横幅以真实 WebSocket open/close 为准，不因周期性 HTTP 健康检查偶发失败而闪烁。
- 断开时记录关闭码和原因并自动指数退避重连；恢复后重新读取历史。
- 重连不会重复消息、重复启动 Turn 或丢失队列。

## E2E-012 Codex 上游流失败与 App Server 生命周期

前置条件：可模拟 Codex 上游 response stream 超时或断开，但保持浏览器到 CodyWork WebSocket 正常。

步骤：

1. 发送消息并触发上游流失败。
2. 观察 provider retry、HTTPS fallback 和最终状态。
3. 继续打开其他页面或从另一个 Tab 查看 Runtime 状态。
4. 恢复上游后手动重试消息。

关键断言：

- 浏览器实时连接和 Codex 上游流是两个独立状态，不把上游失败误报成“后端连接已断开”。
- retry 次数、`willRetry` 和最后活动语义正确；重试耗尽或超时后终止为 failed/disconnected，不能永久 running。
- 提示明确说明“未自动重发”，用户消息和 failed outbox 保留。
- App Server 不因单个 Turn、工具或上游错误自动重启；只有显式部署/运维动作才能重启服务。
- 恢复后手动重试只执行一次。

## E2E-013 图片粘贴、发送与大图预览

前置条件：准备一张不含敏感信息的 PNG 和一张 JPEG。

步骤：

1. 分别通过粘贴和拖入把图片加入 Composer。
2. 删除其中一张，再重新加入。
3. 携带文字发送图片消息。
4. 在时间线点击缩略图，查看大图，再用关闭按钮和 Escape 退出。
5. 刷新页面后再次打开历史图片。

关键断言：

- 粘贴、拖入、预览和移除都有立即反馈；不支持的格式/超限文件有明确错误。
- 图片上传期间不会重复发送，上传失败保留可恢复状态。
- AI 收到的是图片输入，而不是不可访问的本地路径文本。
- 缩略图可点击打开适配视口的大图，支持关闭且不破坏滚动位置。
- 刷新后图片仍可查看。

## E2E-014 工具卡片、Markdown 与长内容

前置条件：一个会产生命令执行、文件变更、GFM 表格、代码块和 Mermaid 的安全任务。

步骤：

1. 发送任务并观察工具卡片从 running 到 terminal 的变化。
2. 展开运行中工具，等待完成。
3. 查看完成后的折叠状态，再手动展开。
4. 操作代码复制、表格 CSV、Markdown 链接和 Mermaid。
5. 在窄视口和宽视口分别检查页面。

关键断言：

- 运行中的工具保持可见；完成后自动收起但可重新展开。
- 相邻同类工具可合理合并，不吞掉失败项和关键信息。
- Markdown、代码、表格和 Mermaid 正确渲染，复制内容准确。
- 长命令、长路径、长 Skill 描述不会撑出页面或造成水平溢出。

## E2E-015 会话沉淀与新会话继承

前置条件：Demand 中已有一轮包含背景、已完成事项、关键决策和待办的对话。

步骤：

1. 从需求工具箱点击“沉淀”。
2. 查看 Demand `docs/` 下已有文档的新增或更新内容。
3. 再次沉淀同一会话。
4. 在同一 Demand 新建会话，询问上一会话的关键决策和剩余工作。

关键断言：

- 沉淀优先更新适合的现有文档，必要时才新建文档，不强制只生成单独 `handover.md`。
- 重复沉淀不会机械复制相同段落。
- 文档明确区分事实、决策、完成项、风险和待办。
- 新会话自动获得 Workspace 知识库、Demand 文档和 Skill 使用引导，无需用户再次手工粘贴上下文。
- 新会话能根据文档回答关键决策；不能声称读取了不存在的内容。

## E2E-016 页面布局、控制台与服务端健康检查（P0）

前置条件：至少覆盖一个常见桌面宽度和一个接近 820px 的窄视口。

步骤：

1. 依次打开概览、需求列表、Demand 会话、知识库、Skills 和设置页。
2. 展开主要弹层、选择器、工具箱和图片预览。
3. 在窄视口重复关键导航和 Composer 操作。
4. 检查浏览器 console 和服务端日志。

关键断言：

- 页面无意外水平滚动、内容遮挡、不可点击按钮或漂移的悬浮控件。
- 主要操作具备可读标签、键盘焦点和足够点击区域；状态不只依靠颜色表达。
- 空态、加载、成功、失败和禁用状态都有明确反馈。
- 浏览器 console 没有新增 error/warn；服务端没有未处理异常或持续重试风暴。

## E2E-017 快捷指令配置、持久化与直接执行

前置条件：Workspace 中存在两个可调用 Skill，Demand 中存在一个会话。

步骤：

1. 从左下角进入“设置”，再进入“快捷指令”。
2. 创建一条唯一名称的指令，填写完整 Prompt，选择两个 Skill，勾选“需求开发”。
3. 刷新当前专属 URL，返回设置总览，再重新进入快捷指令。
4. 进入 Demand，会话空闲时点击该快捷指令。
5. 在另一个 Turn 运行中再次点击该快捷指令。
6. 回到设置停用、编辑、再删除该指令。
7. 在 Demand 会话中明确要求 AI 创建一条唯一名称的快捷指令，指定完整 Prompt、一个默认 Skill 和立即启用；完成后打开工具箱并点击执行。
8. 仅向 AI 表达“这个 Prompt 挺好用”，但不要求创建或保存快捷指令。
9. 用自然语言说“把 xxx 沉淀成快捷指令”，不提供名称，并在 xxx 中引用一个 Skill。

关键断言：

- 设置总览显示正确数量；二级页面 URL 可刷新恢复。
- Skill 支持搜索和多选，长描述不会撑破布局。
- 配置按 Workspace 隔离并存入 SQLite，刷新后完整保留。
- 空闲时点击立即发送；运行中点击进入队列。两种情况都复用正常 Composer/Core 消息链路。
- 快捷执行不覆盖当前草稿、手动 Skill 或待发送图片。
- 停用后 Demand 不显示；删除前有确认，删除后刷新不再出现。
- AI 明确收到创建授权时通过 CodyWork 产品工具落库；设置页显示来源和递增版本，工具箱无需刷新即可看到，点击后仍走结构化 Skill 与正常消息链路。
- 未明确授权创建或更新时，AI 可以建议或询问，但不得写入快捷指令。
- “沉淀成快捷指令”被识别为明确授权；AI 自动提炼短名称，并把引用的 Skill 结构化保存为默认 Skill，而不是只写进 Prompt 文本；本次只保存，不立即执行指令内容。

## E2E-018 快捷指令 Skill 失效

前置条件：创建一条引用一次性测试 Skill 的快捷指令。

步骤：

1. 确认指令可正常显示和执行。
2. 从测试 Workspace 精确移除该 Skill，再刷新 Skills 和设置页。
3. 返回 Demand 查看该指令。
4. 在设置中重新选择有效 Skill 并保存。

关键断言：

- 失效 Skill 不会被静默忽略；配置显示“需修复”或等价状态。
- Demand 中该指令不可执行，并明确指出哪个 Skill 失效。
- 修复配置后立即恢复可执行，不需要重建指令。

## E2E-022 Skill 安装执行面板与手动暂停

前置条件：使用一次性 Workspace，准备一个安装过程可持续观察、且只写入 `.agents/skills/` 的测试 Skill 来源。

步骤：

1. 打开 Skills 页面，输入测试 Skill 来源并点击“安装”。
2. 观察安装请求成功后的首屏状态，以及 Agent 产生思考、命令或文件变更事件后的状态。
3. 收起执行 Dialog，确认任务继续运行；从 Skills 页面摘要重新打开执行记录。
4. 对一条仍在执行的安装点击“暂停执行”，等待任务进入终态。
5. 重新发起安装并允许其运行超过 120 秒，再等待正常完成。
6. 在常见桌面宽度和接近 820px 的窄视口检查 Dialog；用键盘 `Esc` 收起，再刷新 Skills 页面。

关键断言：

- 安装开始后立即打开独立执行 Dialog；状态、耗时、事件数量和 Skill 来源清晰可见。
- Agent 思考、命令输出、文件变更、最终回复和失败信息在可滚动区域内按顺序显示；长内容不会撑出页面。
- 收起 Dialog 不会停止任务；摘要入口持续展示最新状态并可重新打开。
- 任务没有固定自动超时，运行超过 120 秒仍保持执行；仅用户点击“暂停执行”时调用 Runtime interrupt。
- 暂停过程依次显示“暂停中”和“已暂停”，不残留 `running`；界面明确说明既有文件变更不会自动回滚。
- 完成、失败和已暂停都是明确终态，不只依靠颜色表达；暂停按钮可通过键盘聚焦，窄屏无横向溢出。
- 页面刷新不会误报任务仍在运行；服务重启后如内存执行记录不再可用，不得伪造已完成状态。

## E2E-023 会话分享与飞书文档导出

前置条件：配置一个具备云文档创建、内容转换、块写入及权限设置能力的专用测试飞书机器人；准备一个含用户文字、AI Markdown 回复、工具调用、命令输出、图片、Skill 引用和一次中断回复的 Demand 会话，并准备一个 Workspace 会话。不得使用真实业务对话。

关键断言：

- 默认名称包含需求名和会话名；Workspace 会话只包含 Workspace 与会话元数据。用户可在导出前修改标题。
- 每次导出生成独立静态快照，成功态展示实际消息数、可打开链接和复制入口，不暗示实时同步。
- 文档权限明确设置为组织内持链接者只读；权限设置失败时整个操作显示失败，不返回一个用户打不开的“成功”链接。
- 飞书 App Secret 不进入浏览器、文档、日志或错误详情；只使用服务端加密保存的所选机器人凭证。

清理：删除测试导出的飞书文档、一次性会话、Workspace 和测试数据库；不删除正式飞书文档或业务会话。

## E2E-019 权限与网络边界

前置条件：分别创建 read-only、workspace-write 和 yolo 会话；准备当前 Demand Worktree、其他 Demand/用户目录中的无风险可读文件、Worktree 内外两个无风险写入测试路径、一个一次性 bare Git remote，以及一个无敏感数据的网络地址。

步骤：

1. 在三种模式下分别执行网络只读访问。
2. 在三种模式下分别读取 Workspace 外、其他用户目录和全局 Skill 目录中的无风险测试文件。
3. 在 read-only 下尝试写入 Worktree。
4. 在 workspace-write 下写入 Worktree 内文件，再尝试写入 Workspace/Worktree 外的无风险测试路径；如 Codex 请求审批，从页面完成审批后核对结果。
5. 在 workspace-write 下修改一次性仓库文件，提交并推送当前 Demand 分支；如 Codex 请求 Git 元数据或网络权限则正常审批，并从 bare remote 校验提交确实存在。
6. 在 yolo 下分别写入测试 Worktree 内文件和 Workspace 外的唯一临时文件，再次提交、推送当前 Demand 分支。

关键断言：

- 三种模式都允许网络访问。
- 三种模式的读取都不受用户、目录或文件边界限制；全局 Skill 及其依赖可直接读取。
- read-only 拒绝文件写入。
- workspace-write 完整使用 Codex 原生 `workspaceWrite` 和审批策略；CodyWork 不维护第二份路径白名单，也不产生“超出 Demand Worktree”的产品级拒绝。Git 元数据或外部路径是否直接允许、请求审批或拒绝，以当前 Codex Runtime 的原生结果为准。
- yolo 使用 Codex 原生 `dangerFullAccess`，可以提交、推送并访问 CodyWork 服务账号在操作系统层面有权访问的其他目录；CodyWork 不再保留 Demand 文件写入边界。
- read-only、workspace-write、yolo 的实际 Runtime 请求分别携带 `readOnly`、`workspaceWrite`、`dangerFullAccess`，不携带 CodyWork 自定义 permission profile。
- 页面清楚提示 YOLO 是完整系统权限；Normal 的原生审批信息说明目标和原因，不出现 CodyWork 伪造的越界错误或空审批卡。

- 飞书富文本中的文字和图片都被接收；图片/文件安全下载到当前 Demand 的 `docs/.channel-attachments/`，越界文件名被清理，超限资源失败且不写出 Worktree。assistant Markdown 中的受控本地栅格图片被上传为真实飞书图片节点且正文不残留本地路径。
- 审批和问题只能由绑定人处理；任一端完成后另一端冻结为已处理，不能重复执行。
- `/stop` 只中断当前 Turn；`/unbind` 后下一条消息重新绑定；失败消息不会静默重发，只有显式 `/retry` 创建一个新的稳定命令。
- 飞书长连接自动重连且不依赖浏览器 WebSocket；连接问题不触发 Codex App Server 重启。服务重启后，已确认提交的 Turn 继续投影，提交状态不确定的命令标记失败并提示手动重试。

- 设置页能清楚区分连接状态、最近活动、最近一次断开事实、绑定、执行队列、Inbox 和 Outbox；失败投递可人工重试。卡片深链精确打开绑定会话；浏览器内容区不常驻绑定横幅，机器人按钮提供至少 44px 点击区域并按需打开绑定详情弹窗，绑定用户只以脱敏形式展示。浏览器控制台与服务端无未处理异常或重试风暴。
- Workspace 绑定不依赖任何虚构 Demand；已有会话和新建会话都可选择 YOLO 或 Normal，默认推荐 YOLO。实际 Turn 使用绑定保存的权限，支持命令、Git、网络、文件读写和附件；CodyWork 不再叠加 Workspace 文件白名单。

清理：解绑测试会话，删除测试群，删除专用测试账号配置和一次性附件；保留正式 Workspace、Demand、原生 Thread 和业务仓库不动。

## E2E-024 智能完工通知

前置条件：准备一次性 Workspace、一个 Demand、一个 Workspace 会话、一个 Demand 会话，以及一个专用测试飞书机器人和该应用下的接收人 Open ID。真实发送前必须得到用户明确授权。

步骤：

1. 从“设置”进入“智能通知”，确认默认关闭、默认阈值为 30 分钟，通知范围默认包含需求会话和 Workspace 会话。
2. 选择已启用的机器人，填写属于该应用的接收人 Open ID，修改阈值和通知范围并保存；刷新二级页面并从设置总览重新进入。
3. 点击“发送测试通知”，在飞书确认收到私聊卡片。
4. 执行一次低于阈值的普通问答，以及一次持续时间超过阈值但没有工具、文件、计划或验证信号的普通文字回复。
5. 执行一次超过阈值的复杂任务，包含多次工具调用、文件修改和验证；在任务中间制造一段等待审批或等待用户回答，再完成 Turn。
6. 对同一个终态事件执行重放或服务重启恢复，然后分别执行一次超过阈值的失败任务、一个不在已勾选范围内的长任务。
7. 暂时断开飞书连接后完成一个符合条件的长任务，再恢复连接。

关键断言：

- 设置按 Workspace 隔离并持久化；二级 URL 刷新可恢复，未连接或未启用的机器人不能被误认为可立即发送。
- 普通问答和无复杂信号的长文字回复不通知；只有有效执行时间达到阈值且具有复杂任务信号，或达到阈值后失败，才通知。
- 有效执行时间扣除等待审批和等待用户回答的区间，卡片同时展示有效执行时长，不能把等待时间冒充工作时间。
- 卡片通过机器人私聊目标用户，不向来源群刷屏；包含状态、会话名、Workspace、存在时的 Demand、结果摘要、工具/文件/验证摘要及返回原会话的链接。
- 同一个 Turn 使用稳定去重键，无论事件重复、页面刷新或服务重启都最多投递一次。
- 飞书暂时离线时通知先进入持久化 Outbox，恢复后继续投递；通知失败不能影响原始 Codex Turn 的成功或失败状态。
- 关闭功能或取消某个范围后不再发送对应通知；Open ID 明确提示为应用级身份，不能静默复用其他 App 的 Open ID。

清理：关闭一次性 Workspace 的智能通知，删除测试 Outbox、测试机器人配置和一次性 Workspace；真实业务会话与仓库不作为测试清理对象。

## E2E-021 Workspace 会话

前置条件：使用一次性 Workspace，其中包含根 `AGENTS.md`、一个带子目录 `AGENTS.md` 的测试 Repo、一个可识别的代码文件、一份 `docs/` 知识文档和一个可调用 Skill；准备本地 bare remote 供 Git 推送验证。

步骤：

1. 从左侧导航进入“Workspace 会话”，确认空 Workspace 会自动创建第一个会话且默认权限为 YOLO。
2. 新建第二个会话，分别重命名和切换两个会话；复制当前 URL，刷新并在新 Tab 直接打开。
3. 询问代码文件中的唯一标识，再询问知识文档中的唯一事实；使用 `$` 引用测试 Skill 发送一轮。
4. 让 Codex 运行 `pwd`、代码搜索、无敏感网络查询和一个已登录的测试 CLI 状态命令。
5. 让 Codex 在 Workspace 根目录创建测试文件，再修改测试 Repo 文件、提交并推送到 bare remote；核对操作前读取了根及 Repo 目录链上的 `AGENTS.md`。
6. 依次切换 Normal、只读和 YOLO：Normal 验证原生审批，read-only 验证写入被 Codex 沙箱拒绝，YOLO 再次成功写入。
7. 上传测试图片与文件，确认消息可发送、文件可被读取；停止并重启 CodyWork 服务，从专属 URL 恢复同一会话，再执行一次 YOLO 写入。
8. 删除两个 Workspace 会话，包括删除最后一个会话，然后重新进入“Workspace 会话”。

关键断言：

- Workspace 会话是一级会话，URL 只包含 Workspace 和 Conversation，不包含伪造的 Demand。刷新、新 Tab 和服务重启后恢复同一原生 Codex Thread及已保存权限。
- 会话可读整个 Workspace，能根据 Workspace knowledge catalog 按需读取知识，支持多轮和 `$Skill`，不把全部知识或 Skill 默认塞入上下文。
- 新会话默认 YOLO；Composer 同时提供只读、Normal 和 YOLO，切换立即持久化。YOLO 使用底层 `dangerFullAccess`，Normal 使用底层 `workspaceWrite` 与审批，只读使用底层 `readOnly`；CodyWork 不再额外限制 Workspace 文件、Git、CLI 或网络。
- 根 `AGENTS.md` 在创建会话时注入；操作具体 Repo 前按目录链读取更深层 `AGENTS.md`，不会无差别把所有 Service 规则塞入初始上下文。
- Workspace 附件可安全落到 `docs/.channel-attachments/`；文件名清理、大小限制和图片输入行为与 Demand 通道一致。
- Workspace 会话不要求 Demand 专属的保底数量；删除最后一个后回到稳定空态，再进入时创建新会话。
- 消息顺序、optimistic 气泡、工具卡片、Worked 终态和 WebSocket 重连语义与 Demand 会话共享同一套 Core 链路，无重复实现和重复消息。

清理：删除一次性 Workspace 与测试数据库，停止测试进程；确认未修改或清理任何真实用户仓库。
